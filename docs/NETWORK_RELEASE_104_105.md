# AetherMind — исправление проверки каталога, выпуск 104/105

Основание: выпуск 103 применил миграции `202610100001`–`202610100003`,
затем остановился на проверке Node Alpha и вернул прежний код.
Исходный коммит: `a27b280b3e1f79da4bbb3e592edf06c9a8063ec1`.

## Причина и исправление

Первоначальная миграция каталога оставляла `max_per_user` равным 5/3/2.
Предыдущий GPU Live деплой принимал любой положительный лимит.
Выпуск Network стал требовать 1, но не добавил миграцию этого поля.
Интеграционные fixtures устанавливали 1 вручную и скрыли этот пропуск.

Добавлена `202610100004_catalog_tariff_limit`: только `max_per_user=1`
для Alpha/Beta/Enterprise. Уже применённые миграции не редактируются.
Цены, проценты, сроки, total/available supply, договоры, LedgerEntry,
акцепты и накопленные вознаграждения эта миграция не изменяет.

Проверка каталога вынесена в `ops/network-catalog-check.py`:
точное сравнение Decimal, перечисление всех конкретных расхождений,
проверка остатков и резервов. До миграции допускается положительный
старый лимит; после неё строго требуется 1.
Каталог проверяется до остановки API/watcher, затем после остановки
перед финальными миграциями и после них. Снимки до/после должны совпасть
во всех полях, кроме `max_per_user`. Ошибочная ставка или нехватка
резерва не исправляются подстановкой новых финансовых данных.

## Повторный запуск после отката

Скачать новые 104/105 и выполнить в Termux:

```bash
bash ~/storage/downloads/104_aethermind_network_github.sh
bash ~/storage/downloads/105_aethermind_network_vps.sh
```

104 отправляет дополнительный коммит обычным push и сохраняет точный SHA.
105 разворачивает именно этот SHA. Все проверки PostgreSQL из 103,
финальный backup, защита TON, оферты и безопасного отката сохраняются.
Prisma пропускает уже успешно применённые миграции и выполняет новую.
Если повторный запуск отклоняет другие параметры, он показывает поле,
фактическое и ожидаемое значение; денежные условия автоматически не меняет.

При ошибке до переключения старый код восстанавливается; данные не
восстанавливаются из дампа поверх новых операций. Установленный лимит 1
совместим с прежним кодом, который уже запрещает второй активный договор.
Исходный backup `/srv/backups/gpunode/network-103-20261010T193040Z`
сохраняется. Новый backup: `/srv/backups/gpunode/network-105-<UTC>`.

Публикация оферты, правила 4.3, политика пяти денежных трактовок,
подтверждение исторических выплат и процедуры безопасного восстановления
описаны в `docs/NETWORK_RELEASE_102_103.md` и не меняются этим исправлением.

## Проверки

Регрессия использует фактические SQL миграции до уже применённого
`202610100003`, а не каталог с вручную заданным лимитом 1.
Проверены переход 5/3/2 → 1/1/1, сохранность всех остальных полей,
действующего legacy договора, баланса и акцепта, повтор без новых изменений.
Fixtures деплоя проверяют прежние лимиты, эквивалентные десятичные записи,
расхождения денежных условий, недопустимый остаток и некорректные числа.
Повторные production проверки выполняются 105 на сервере; локальные
проверки не объявляются фактическим production деплоем.
