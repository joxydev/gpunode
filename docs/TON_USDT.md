# USDT на TON Mainnet · AetherMind

Доступен только официальный USDT Jetton Master `EQCxE6mUtQJKFnGfaROTKOt1lZbDiiX1kCixRv7Nw2Id_sDs` и treasury `UQBHmBs516S1EKkDLj9K-hwCD-WlvRn05ieMiScK-pBBO8iH`. Токены из других сетей и токены с таким же названием не учитываются. Treasury seed/private key серверу не требуются.

## Граница этапа

- Пополнение внутреннего реального баланса через TON Connect → TON Proof → invoice → Jetton transfer → watcher → atomic ledger.
- При `ENABLE_TON_USDT_DEPOSITS=true` счёт доступен всем авторизованным пользователям с подтверждённым TON-кошельком. Если TON Center недоступен, API не создаёт новые счета.
- Заказы за реальный баланс и начисления дохода не запущены. Вывод запрашивается через поддержку и рассматривается оператором вручную. Исторические тестовые записи сохраняются в базе для аудита и отката, но доступ к их начислению удалён.
- TON Center API key вводится только в терминале VPS, хранится в `/srv/apps/gpunode/shared/runtime.env`; `.env.example` содержит пустой ключ.

## Резерв GRAM для обычного TON Connect перевода

`TON_JETTON_ATTACH_GRAM` задаётся **только на сервере** и превращается в целое число нанограмов. Это сумма, прикладываемая к сообщению в Jetton Wallet для исполнения перевода, **не фактическая комиссия сети** и не сумма USDT. Внутри payload неизменны: официальный master, treasury, `queryId`, `AETHERMIND:<invoiceId>`, `response_destination = sender` и `forward_ton_amount = 1` нанограм. Неиспользованный резерв Jetton Wallet может вернуть отправителю; собственные сетевые комиссии кошелёк показывает отдельно.

В `.env.example` кандидат `0.05` GRAM. Официальный пример TON использует `0.05` для более простого Jetton transfer; для нашего payload с комментарием достаточность проверяется реальным Mainnet trace. При развёртывании этого промежуточного этапа публичный резерв явно фиксируется прежним `0.1` в `runtime.env`, а `TON_JETTON_ATTACH_SMOKE_OWNER_GRAM=0.05` применяется только к `OWNER_TELEGRAM_ID` и отдельному списку `TON_PAYMENT_TEST_TELEGRAM_IDS`. Первый добавленный тестовый ID — `6662169510` (`@VerstakPR`); разрешение даёт только платёжный canary, не права владельца. Идентификация идёт по подписанной Telegram-сессии и числовому ID, а не по изменяемому username. Публично `0.05` включается только после проверенного trace. При первом развёртывании `ENABLE_TON_GASLESS=false`; успешный ответ кошелька или relayer не начисляет баланс. Последующие обновления сохраняют отдельно проверенные значения публичного резерва и gasless.

Для проверки тестовый аккаунт `6662169510` подключает отдельный от treasury TON кошелёк, создаёт новый счёт на минимальную сумму (от 1 USDT), подтверждает перевод и передаёт оператору invoice ID и hash. Оператор проверяет trace успешного Jetton transfer, достаточность `0.05` для комментария и `transfer_notification`, сумму на treasury, фактический расход GRAM и возврат excess, статус `CREDITED`, одну запись `wallet_ledger` и одну `LedgerEntry`. Кошелёк самого treasury нельзя использовать как отправителя депозита и он не подходит для smoke-теста. Без этих наблюдений публичное значение не изменять. При недостатке средств изучить trace и эмульцию, подобрать измеренное значение с небольшим запасом. Отмена invoice после отправки транзакции не прекращает перевод; платежу может потребоваться ручная сверка.

## TON Proof и gasless (закрытый флаг)

После успешного TON Proof сервер хранит подтверждённый открытый ключ и версию кода кошелька. Ранее привязанные кошельки продолжат обычные переводы; для gasless им нужен новый proof. Проверенный W5 сам по себе недостаточен: приложение использует `signMessage` только если кошелёк явно объявил feature `SignMessage`, серверный флаг `ENABLE_TON_GASLESS=true`, задан отдельный `TONAPI_API_KEY` и relayer TONAPI подтвердил поддержку официального USDT. Имя `telegram-wallet` и W5 не служат доказательством capability. `TONCENTER_API_KEY` и `TONAPI_API_KEY` предназначены для разных сервисов.

Сервер строит один invoice, сохраняет оценку relayer и сверяет два Jetton-сообщения: точную сумму и комментарий `AETHERMIND:<invoiceId>` в treasury, отдельную комиссию USDT для relayer. Комиссия показана до подписи. После `signMessage` backend проверяет W5-подпись открытым ключом TON Proof, точный набор получателей, payload, суммы и срок. Только тот же подписанный BoC может повторно поступить к relayer при сбое ответа. Обычный перевод автоматически не запускается после подписи. Успех relayer **не зачисляет** деньги: действующий watcher и атомарный ledger являются единственным источником подтверждения.

При отсутствии `SignMessage` либо ключа TONAPI используется обычный перевод; публичный резерв до подтверждённого Mainnet trace остаётся `0.1` GRAM. Кошельки, объявляющие structured `jetton`, могут сами оценить attach через серверный structured item с теми же invoice/query ID. В остальных случаях используется серверный raw payload. В `.env.example` кандидат обычного резерва `0.05`, gasless остаётся выключен. Запрещено включать газлесс всем без проверки реального W5-кошелька с `SignMessage`, точной комиссии, поступления в treasury и единственного зачисления.

### Выпуск по этапам на VPS

После сборки, `npm test`, фронтенд-сборки и VPS CI первое развёртывание оставляет публичный raw attach `0.1` и gasless выключенным. Скрипт `ops/ton-promote-vps.sh` проверяет реальный invoice **владельца или тестового ID**, tx hash, `CREDITED`, точную сумму, привязку treasury/master, отличие отправителя от treasury и ровно одну запись в обоих ledger. Он выводит trace для проверки человеком. Порядок:

1. `sudo bash /srv/apps/gpunode/current/ops/ton-promote-vps.sh standard dep_<ID> <HASH>` — тестер проводит новый raw Mainnet-платёж с `0.05`, оператор проверяет trace и возврат excess. Пока canary включён, сервер не предлагает тестеру structured Jetton item, чтобы кошелёк не подменил измеряемый attach своей оценкой.
2. `sudo bash /srv/apps/gpunode/current/ops/ton-promote-vps.sh gasless-canary` — отдельно ввести **ключ TONAPI**, проверить поддерживаемый USDT master, открыть gasless только владельцу и тестовому ID.
3. Тестер с W5 и **объявленным кошельком** `SignMessage` проводит небольшой Mainnet gasless-перевод: точная комиссия USDT до подписи, без GRAM, USDT на treasury, один credit, проверенный trace.
4. `sudo bash /srv/apps/gpunode/current/ops/ton-promote-vps.sh gasless-all dep_<ID> <HASH>` — после этого gasless становится доступен другим совместимым кошелькам. Telegram Wallet без `SignMessage` остаётся в STANDARD.

Если кошелёк тестера не объявляет `SignMessage` или отсутствует trace, газлесс публично не включать; стандартный способ остаётся доступен. Для invoice из старого релиза без `standardAttachNano` нужен новый smoke invoice. Тестер видит только диагностическую вкладку своего TON Connect в разделе кошелька, без доступа к панели владельца или серверным ключам. Секреты не выводятся в журнал, флаги хранятся только в `runtime.env` (0600), для каждой смены создаётся резервная копия конфигурации.

## Цепочка проверки

Пользовательский аккаунт должен принять актуальные документы. После TON Proof адрес подтверждается криптографической подписью nonce и сохраняется в `user_wallets`. При создании счёта сервер сам назначает master, получателя, точную сумму в микродолларах USDT (Jetton decimals = 6), query ID, время действия и одноразовый invoice ID. Только сервер формирует Jetton transfer body для TON Connect. Успешный ответ кошелька не меняет баланс.

Отдельная служба `gpunode-ton-watcher.service` опрашивает финализированные транзакции treasury через TON Center v3. Входящее `transfer_notification` должно поступить от Jetton Wallet, полученного с официального master методом `get_wallet_address(treasury)`; перевод не должен быть bounced/aborted, должен иметь нужный opcode, sender, invoice, query ID и точную сумму. Счёт, учётная запись и запись в `wallet_ledger` обновляются в одной транзакции PostgreSQL, с блокировкой пользователя и счёта. Повторное обнаружение транзакции возвращает `ALREADY_CREDITED`.

Недостаточная/избыточная сумма и перевод после expiry идут в `MANUAL_REVIEW`; отсутствие invoice или чужой sender попадает в `unmatched_ton_deposits`. Дополнительная сверка `/jetton/transfers` показывает владельцу реальные индексированные переводы без пригодного уведомления, но **никогда не зачисляет** их автоматически. Подтверждённые переводы, совершённые **до** expiry, учитываются и после появления в индексаторе. Сбои индексатора не переводят счёт в FAILED: cursor сохраняется только после полного прохода, worker повторяет проход с перекрытием и отложенными счетами.

## Перед публичным запуском

1. Владелец проверяет подлинный доступ к treasury и доступность TON Center в разделе «Управление» → «Депозиты». Бот и TLS сертификат должны работать по HTTPS.
2. Владелец подключает реальный TON-кошелёк, подписывает TON Proof, отправляет небольшую сумму USDT TON (от 1 USDT) и проверяет идентификатор счёта, поступление в treasury, `CREDITED`, баланс, ровно одну запись `wallet_ledger`, уведомление и ссылку на explorer.
3. Проверяются ошибки и восстановление после сбоя TON Center и перезапуска worker. Если transfer есть, а зачисления нет, деньги требуют ручной сверки. Нельзя включать публичные пополнения только по успешным unit тестам.
4. Скрипт релиза включает публичные счета только при наличии ключа и после проверки официального Jetton master и индексатора TON Center. Отмена ожидающего счёта освобождает слот. Перевод, совершённый по отменённому счёту, подлежит сверке в блокчейне и зачислению либо ручной проверке.

Запись в старой `LedgerEntry` сохраняется для совместимости с профилем. Каждому депозиту соответствует ровно один `wallet_ledger` и один `LedgerEntry` по уникальному `sourceId`. Проверки на VPS: `npm test`, `npm run build`, `ops/vps-ci.py` с отдельной БД и HTTP-набором; конфиг Nginx дополнен публичным TON Connect manifest и соединениями кошельков по HTTPS/WSS.
