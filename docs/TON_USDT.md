# USDT на TON Mainnet · AetherMind

Доступен только официальный USDT Jetton Master `EQCxE6mUtQJKFnGfaROTKOt1lZbDiiX1kCixRv7Nw2Id_sDs` и treasury `UQBHmBs516S1EKkDLj9K-hwCD-WlvRn05ieMiScK-pBBO8iH`. Токены из других сетей и токены с таким же названием не учитываются. Treasury seed/private key серверу не требуются.

## Граница этапа

- Пополнение внутреннего реального баланса через TON Connect → TON Proof → invoice → Jetton transfer → watcher → atomic ledger.
- При запуске `ENABLE_TON_USDT_DEPOSITS=false`: новый invoice может создать только Telegram аккаунт владельца (`OWNER_TELEGRAM_ID`) для проверки Mainnet. Остальные пользователи могут подключить и подтвердить кошелёк, но не отправить USDT через приложение.
- Реальные заказы GPU, начисления дохода, вывод средств и начисление рефералам всё ещё выключены. Тестовые заказы используют отдельную таблицу и отдельный баланс.
- TON Center API key вводится только в терминале VPS, хранится в `/srv/apps/gpunode/shared/runtime.env`; `.env.example` содержит пустой ключ.

## Цепочка проверки

Пользовательский аккаунт должен принять актуальные документы. После TON Proof адрес подтверждается криптографической подписью nonce и сохраняется в `user_wallets`. При создании счёта сервер сам назначает master, получателя, точную сумму в микродолларах USDT (Jetton decimals = 6), query ID, время действия и одноразовый invoice ID. Только сервер формирует Jetton transfer body для TON Connect. Успешный ответ кошелька не меняет баланс.

Отдельная служба `gpunode-ton-watcher.service` опрашивает финализированные транзакции treasury через TON Center v3. Входящее `transfer_notification` должно поступить от Jetton Wallet, полученного с официального master методом `get_wallet_address(treasury)`; перевод не должен быть bounced/aborted, должен иметь нужный opcode, sender, invoice, query ID и точную сумму. Счёт, учётная запись и запись в `wallet_ledger` обновляются в одной транзакции PostgreSQL, с блокировкой пользователя и счёта. Повторное обнаружение транзакции возвращает `ALREADY_CREDITED`.

Недостаточная/избыточная сумма и перевод после expiry идут в `MANUAL_REVIEW`; отсутствие invoice или чужой sender попадает в `unmatched_ton_deposits`. Дополнительная сверка `/jetton/transfers` показывает владельцу реальные индексированные переводы без пригодного уведомления, но **никогда не зачисляет** их автоматически. Подтверждённые переводы, совершённые **до** expiry, учитываются и после появления в индексаторе. Сбои индексатора не переводят счёт в FAILED: cursor сохраняется только после полного прохода, worker повторяет проход с перекрытием и отложенными счетами.

## Перед публичным запуском

1. Владелец проверяет подлинный доступ к treasury и доступность TON Center в разделе «Управление» → «Депозиты». Бот и TLS сертификат должны работать по HTTPS.
2. Владелец подключает реальный TON-кошелёк, подписывает TON Proof, отправляет небольшую сумму USDT TON (от 1 USDT) и проверяет идентификатор счёта, поступление в treasury, `CREDITED`, баланс, ровно одну запись `wallet_ledger`, уведомление и ссылку на explorer.
3. Проверяются ошибки и восстановление после сбоя TON Center и перезапуска worker. Если transfer есть, а зачисления нет, деньги требуют ручной сверки. Нельзя включать публичные пополнения только по успешным unit тестам.
4. После успешной реальной проверки отдельным управляемым изменением `runtime.env` допускается установить `ENABLE_TON_USDT_DEPOSITS=true` и перезапустить API. Публичный запуск также требует актуальных условий оферты и регламента работы с реальными депозитами.

Запись в старой `LedgerEntry` сохраняется для совместимости с профилем. Каждому депозиту соответствует ровно один `wallet_ledger` и один `LedgerEntry` по уникальному `sourceId`. Проверки на VPS: `npm test`, `npm run build`, `ops/vps-ci.py` с отдельной БД и HTTP-набором; конфиг Nginx дополнен публичным TON Connect manifest и соединениями кошельков по HTTPS/WSS.
