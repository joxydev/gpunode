# AetherMind · депозиты USDT в TON

Поддерживается только официальный USDT Jetton TON Mainnet. Адрес Jetton Master и адрес казначейства зафиксированы в серверной конфигурации и проверяются при запуске. TON Connect отправляет платёж, но баланс зачисляет только watcher после успешного on-chain `transfer_notification` с правильными sender, Jetton Wallet, invoice, query ID и суммой. Одна транзакция PostgreSQL обновляет депозит, `wallet_ledger` и `LedgerEntry`. Ни `sendTransaction`, ни `signMessage`, ни ответ relayer не подтверждают платёж.

## Почему предыдущие платежи зависли

26 и 27 сентября 2026 года USDT дошли до Jetton Wallet казначейства. Уведомление на owner адресе содержало 1 нанограмм и завершилось `aborted/no_gas`; watcher правильно отказался начислять баланс. Баланс owner адреса выше 0,02 GRAM не помог: compute phase входящего сообщения ограничивается суммой, полученной **с этим сообщением**. Ручные сверки инцидентов не считаются проверкой нового платёжного контура.

Отдельные параметры:

| Серверный параметр | Первоначальное значение | Назначение |
| --- | ---: | --- |
| `TON_JETTON_ATTACH_GRAM` | 0,1 | Исполнение обычного Jetton transfer в кошельке отправителя; это не фактическая комиссия. |
| `TON_NOTIFICATION_FORWARD_GRAM` | 0,02 | Финансирование сообщения `transfer_notification` на казначейский owner адрес. |
| `TON_GASLESS_ATTACH_GRAM` | 0,1 | Исполнение Jetton transfer через relayer; relayer определяет отдельную комиссию в USDT. |
| `TON_TREASURY_MIN_GRAM` | 0,02 | Дополнительная проверка доступности owner адреса, не доказательство успешной обработки уведомления. |

Значение 0,02 для уведомления взято из [примера TON](https://docs.ton.org/contracts/standard/tokens/jettons/transfer), это **кандидат для Mainnet canary**. Его достаточность для конкретного кошелька, комментария и текущих комиссий доказывает только успешный реальный trace. Изменение сумм в `runtime.env` требует повторного canary. Все значения проверяются как целые nanogram, и attached amount обязан оставить резерв на работу Jetton Wallet. В structured Jetton item кошелёк может сам определить общий attach, но `forwardAmount` остаётся серверным.

## Режимы

`TON_DEPOSIT_ACCESS=disabled|canary|public` задаёт доступ к **новым** invoice; проверка существующих платежей продолжается во всех режимах. При `canary` invoice доступны владельцу и числовым ID из `TON_PAYMENT_TEST_TELEGRAM_IDS`; это не даёт права доступа к панели владельца. Gasless-релиз сохраняет точное действующее значение `TON_DEPOSIT_ACCESS` и параметры уже проверенного обычного перевода, но выключает `ENABLE_TON_GASLESS` до отдельного canary. Если режим текущего сервера неизвестен, деплой прекращается. Новый явный режим `disabled` имеет приоритет над прежним `ENABLE_TON_USDT_DEPOSITS=true`.

Новый релиз запускают двумя Termux скриптами: GitHub, затем VPS. Сборка и HTTP набор на отдельной PostgreSQL выполняются на VPS до переключения сайта. Для действующих счетов watcher работает и при отключении новых. Конфигурация сохраняется в закрытом `runtime.env`, релиз имеет резервную копию.

Для первоначального открытия обычных депозитов после их отдельного релиза:

1. `sudo bash /srv/apps/gpunode/current/ops/ton-promote-vps.sh deposits-canary` открывает только владельцу и уже внесённым тестовым ID.
2. Проведите **новый** платёж от отдельного пользовательского TON кошелька, минимум 1 USDT, обычным `sendTransaction`. Не используйте treasury как отправителя.
3. Дождитесь автоматического `CREDITED` и пришлите новый invoice ID и **64 символа hex tx hash входящего уведомления казначейства**. Его можно взять из истории депозита/owner уведомления. Trace должен иметь `aborted=false`, `compute_ph.success=true`; поступление USDT и корректный `forward_ton_amount` проверяет gate.
4. `sudo bash /srv/apps/gpunode/current/ops/ton-promote-vps.sh deposits-public dep_<ID> <HEX_HASH>` проверяет запись в двух ledger, отсутствие ручной сверки, on-chain уведомление с официальным Jetton Wallet, индексированный USDT перевод и forward. Только после этого открывается публичный приём.

Если canary снова зависнет, оставьте публичные счета закрытыми: `sudo bash /srv/apps/gpunode/current/ops/ton-promote-vps.sh deposits-off`. Изучите trace и фактически полученный owner адресом GRAM, затем измените `TON_NOTIFICATION_FORWARD_GRAM` и при необходимости attach, повторите новый canary. Не делайте автоматического зачисления только по индексу USDT transfer.

## Gasless отдельно

Газлесс доступен только когда проверен TON Proof кошелька W5, кошелёк **сам объявляет** `SignMessage` в TON Connect, есть отдельный `TONAPI_API_KEY`, TONAPI поддерживает официальный USDT, пройден стандартный canary. `@wallet` нельзя считать совместимым по имени или версии контракта; без `SignMessage` ему предлагается обычный перевод с GRAM.

`gasless-canary` после публичного стандартного режима запросит ключ TONAPI скрытым вводом, проверит relayer и откроет режим только владельцу и тестовым ID. Кошелёк должен объявлять `SignMessage` с `maxMessages` не менее 2. TONAPI estimate даёт точные два действия: полная сумма invoice в казначейство и отдельная комиссия USDT relayer. Backend проверяет оба, подпись W5 и экономические действия; frontend не формирует перевод самостоятельно. Подписанный BoC может повторно отправляться только в неизменном виде; автоматического второго обычного перевода нет. После отдельного реального W5 платежа без баланса GRAM, успешного trace и ровно одного credit режим `gasless-all dep_<НОВЫЙ_ID> <HEX_HASH>` дополнительно проверяет в том же trace отдельный успешный перевод точной USDT-комиссии от пользовательского Jetton Wallet к relayer. Старые стандартные и ручные зачисления не подходят для этого gate. Ключи не передаются клиенту; seed и private key нигде на VPS нет.

Для диагностики владельцу доступен `/api/v1/ton/health`: TON Center, TONAPI, режим счёта, величины attach и forward, баланс казначейства. Watcher отдельно показывает пропущенные и необработанные операции; indexed transfer без успешного owner уведомления всегда отправляется на ручную проверку.
