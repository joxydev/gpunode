## Пять решений владельца

В «Управление → Партнёры» поля изначально пусты. Версия политики сохраняется
вместе с актором, временем и объяснением. Новая версия не повторяет уже
выплаченные ранговые бонусы и не переписывает замороженные снимки.

| Решение | Доступные варианты |
|---|---|
| Первичная активация | Каждый договор; первый договор тарифа; только внешние TON-средства с FIFO учётом их расходования |
| Командный оборот | Активный principal; накопленный первичный оборот |
| Ранг и права | Текущая активная квалификация; сохранение достигнутого ранга и прежних прав |
| Лидер первой линии | Разрыв у ближайшего лидера включая первую линию; ожидание разбора спорных случаев буквальной трактовки |
| Момент квалификации | До события достижения; включая это событие |

До утверждения зависимые расчёты показывают причину ожидания; известная первая
линия продолжает рассчитываться по 7% активации и 10% суточной прибыли.
Спорная первая линия 1% удерживает только спорные доли: остальные доли периода
проводятся. Решение о разрыве добавляет отдельный неизменяемый план разрешения
на основе первоначального снимка; повтор не создаёт новую выплату.
Совпадение TON-адреса сохраняется для проверки владельцем и само по себе не
объявляется злоупотреблением и не блокирует деньги.

## Денежные проверки

- Активация 50 USDT: 3.50 / 1.50 / 0.50 по линиям 1/2/3.
- Подтверждённая суточная прибыль 0.75: 0.075 / 0.0375 / 0.015.
- Ранги 500 и 2 500: одна выплата; смена политики и повтор обработки не повторяют её.
  Активация личного GPU после достижения командного порога также учитывается.
- 1%: 10 000 → 100; самостоятельная действующая ветка 8 000 → 80;
  завершённые досрочно 2 000 исключаются из текущего периода. Подструктура
  ближайшего Cluster не оплачивается повторно вышестоящему лидеру.
- 2%: фактические комиссии 1 000 → общий пул 20. При весах 3:7 доли 6 и 14.
  В HTTP fixture веса 60 000 и 140 000, чтобы оба участника действительно
  удовлетворяли активной квалификации Enterprise.
- Окно пула буквально `[S − 30 дней, S)`. В феврале соседние окна могут
  перекрываться, после месяца с 31 днём возможен однодневный промежуток.
  Комиссия дедуплицируется внутри снимка, а не между месяцами. Календарный
  месяц, перенос остатка и альтернативная формула не подставлены.
- Крупнейший дробный остаток, затем лексикографический userId: распределяется
  ровно весь пул micro-USDT. Нет участников — UNDISTRIBUTED; F=0 — закрытие
  без денежной проводки; автоматического переноса в следующий пул нет.
- Зафиксированный состав на S сохраняется после последующего раннего выхода.
  Проверены 101 получатель, сбой после части выплат и повтор из сохранённого
  плана. Суточные источники должны пройти Epoch watermark до фиксации снимка.

## Миграции

1. `202610100001_multi_tariff`: preflight конфликтов, индексы аренды/прежних
   запросов и транзакционная защита смешанных резервов.

   индекс `(network,address)`, отдельный userId и неизменяемая история связей.
3. `202610100003_ambassador_network`: дерево, политика, источники и outbox,
   начисления, carry, ранги, периоды, неизменяемые разрешения спорных долей,
   отчёты истории и проверки владельца. Ledger и акцепты не переписываются.

Старые активации/суточные расчёты/комиссии импортируются как HISTORY.
До любого исторического зачисления нужен read-only dry-run, проверка полного
отчёта и утверждение точного `reportHash`. Деплой не утверждает историю.
Неизвестные legacy terms требуют отдельного подтверждённого разбора.

## Проверки выпуска

- Node 24.19 локально; production pipeline использует имеющийся Node 22 VPS.
- `npm test`: 53 backend + 6 frontend, без ошибок.
- `npm run build`: успешно. Vite сообщает о большом основном JS chunk;
  предупреждение не препятствует сборке.
- Все 21 SQL миграции и шесть HTTP-наборов выполнены через Nest/Prisma
  на отдельном PostgreSQL-совместимом PGlite. Это не native PostgreSQL и не
  доказательство параллельности настоящих серверных сессий.
- Native PostgreSQL HTTP, Epoch CLI, advisory lock, 101 аренда и новый
  Ambassador CLI lock обязательно запускаются `ops/vps-ci.py` в отдельном
  временном кластере до миграции рабочей базы. Локально native PostgreSQL
  недоступен; эти проверки здесь не объявляются пройденными.
- 391 уникальное состояние browser QA: RU/EN/RO; пользователь/владелец; 320/360/390/430/768/
  1024/1440 и 844×390; восемь экранов, owner rules, toast/native dialog,
  reduced motion, увеличение текста 200%. Скриншоты проверены визуально.
- Восемь Chromium CPU traces: главная, три GPU, modal, партнёры — до/после,
  один Chromium, CPU throttle ×4. rAF p95 около 16.7–16.8 мс в 2.5-секундных
  пробах. Synthetic UI fixtures и software rendering; это не измерение FPS
  на реальном телефоне. Метрики браузерного CPU приводятся вместе с trace,
  не как утверждение о гарантированной производительности устройств.
- Проверены отдельные fixtures публикации, семидневного срока, выборочного
  изменения Nginx, восстановления частично изменённых конфигураций, literal
  environment и удаления секретов из вывода. Проверены синтаксис shell/Python
  и суммы PDF/архива. Реальные TON-переводы и production выплаты не выполнялись.

## Запуск и восстановление

Сначала `102_aethermind_network_github.sh`, затем `103_aethermind_network_vps.sh`.
102 сохраняет резервную ветку и локальные изменения, объединяет совместимые
изменения main и делает обычный push. Сборка Actions автоматически не запускается.
Точный отправленный SHA сохраняется в `.git/aethermind-network-release`.
103 собирает именно этот SHA, не произвольный позднейший main.

103 использует короткий SSH control socket возле ключа, сверяет целостность
обоих файлов и архива, последовательно собирает и тестирует. Затем создаёт
финальный бэкап при остановленных обработчиках, повторяет preflight, мигрирует,
проверяет исходные остатки, устанавливает службы и проверяет API/Nginx/TON.
Рабочие слоты не заменяются тестовыми числами. Архив SQL не читается postgres
из закрытого root-каталога: запросы поступают через stdin/аргументы.

Бэкап: `/srv/backups/gpunode/network-103-<UTC>`; содержит previous-release,
environment, unit files, Nginx, два db dumps, preflight, публикацию и dry-run.
Финансовая БД при автоматическом откате никогда не восстанавливается из dump.
Дамп предназначен для контролируемого аварийного восстановления после отдельного
разбора, а не для удаления новых операций.

Если новые связи/одновременные тарифы/акцепты/AMB проводки ещё не появились,
скрипт восстанавливает прежний код, настройки, Nginx и прежнее состояние таймеров.
При несовместимом новом использовании оставляет текущий код и данные, останавливает
только Ambassador timer и печатает необходимость исправляющего выпуска.
API, TON watcher и Epoch продолжают обслуживание. После исправления повторяют
эти же два файла или следующий выпуск; dump поверх рабочей базы не накатывают.
